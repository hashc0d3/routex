# RouteX — mesh, реле и мультипуть (что сказал заказчик)

Источник правды по **data plane**. Если формулировка заказчика и старая дока («один PoP») расходятся — побеждает этот файл.

## Как читать его слова

| Сказано | Имеется в виду |
|---|---|
| «Научиться перенаправлять трафик на небольшой мети» | **Мети = mesh.** Не 20 регионов. Сначала **маленькая сеть из 2–3 Debian-релеев**, на ней отладить *куда слать пакет* (steer), а не маркетинг ExitLag. |
| «На них встанет Debian и релей-сервера, для связки и пиринга» | Закупленные машины = **релеи**. Между собой они **пирятся** (полносвязный или почти полносвязный overlay): R1↔R2↔R3. Клиент ходит в эту сетку, пакет может идти `ПК → R1 → R3 → игра`, не только `ПК → один PoP → игра`. |
| «Клиент одновременно поддерживает от 2 до 3 подключений» | **Не failover «порвали WG и подняли другой».** В сессии **2–3 туннеля живы сразу** (handshake уже сделан). |
| «Трафик надо гонять по них одновременно» | Полезный игровой UDP идёт **по нескольким путям сразу**, не «один рабочий + два спят». |
| «Чтобы переключение между каналами не сильно влияло на качество пакетов до сервиса» | **Зачем** мультипуть: смена лучшего канала **не должна** давать дыру (новый handshake, burst loss, скачок jitter). Сервис = игровой сервер. |

Это не «VPN с ручным выбором сервера» и не MPTCP (игры на UDP).

## Как это устроено

```
                    ┌─ path1 ─ R1 ─┐
  Игра (PID) → engine ├─ path2 ─ R2 ─┼─ mesh peering ─ Rx (exit) → игровой сервер
                    └─ path3 ─ R3 ─┘
```

- **Engine** режет трафик выбранного процесса, вешает на пакет свой заголовок: `seq`, `session_id`, `path_id`.
- Шлёт **копии** (или FEC) в 2–3 уже поднятых туннеля.
- Релеи знают соседей (пиринги) и форвардят к **exit** — узлу ближе к игровому IP.
- Exit: **первая копия с данным seq побеждает**, остальное drop. Дальше обычный UDP к игре.
- Обратно: exit шлёт на 2–3 пути (или best+second); engine дедупит и отдаёт процессу.

«Переключение канала» = смена весов/предпочтения, **без разрыва сессии**. Мёртвый путь просто перестаёт давать первые копии; живые уже несут тот же `seq`.

Дублирование жрёт 2–3× трафик клиента. Для игр обычно десятки–сотни кбит/с — приемлемо. **Не** чередовать пакеты round-robin без дедупа: реордер убивает шутеры сильнее, чем лишний байт.

WireGuard (или свой UDP) = **труба до релея**. Логика bonding/dedup — **userspace Go** (engine + pop-agent), не «три независимых WG без общего seq».

## Правила продукта (зафиксировано)

1. Сессия клиента: **min 2, max 3** одновременных path. Один path в проде — только деградация (остался один живой релей), UI показывает degraded.
2. Релеи Debian, между ними **постоянный пиринг** (WG mesh + pop-agent знает граф).
3. Control plane (`routing`) выдаёт: список path (host, port, token), кто **exit** для этой игры/региона, граф соседей.
4. Kill-switch по-прежнему выкл. Падение всех path → трафик игры как без RouteX (fail-open), не чёрная дыра.
5. Скоринг Auto: не LLM; выбирает набор из 2–3 релеев + exit по probe RTT/jitter/loss и load.

---

## Что не делать

- Один туннель и «переключиться на другой сервер» кнопкой как основной UX.
- Держать 2–3 WG только как hot-standby **без** гона игровых пакетов (это не то, что заказал; standby можно как доп. режим позже).
- Тащить mesh через Nest.
- Склеивать пути на TCP.

## Этапы относительно железа

| Когда | Что |
|---|---|
| Сейчас 1× Debian | Протокол и pop-agent: два WG-интерфейса/namespace на одной машине = **имитация 2 path** (не настоящая гео-сетка). Engine proto уже repeated paths. |
| Понедельник, 2–3 сервера | Настоящий маленький mesh: Debian + peering + клиент 2–3 сессии. Цель фразы «научиться на небольшой мети». |
| Дальше | Больше регионов, выбор exit по гео игры, FEC вместо голого dup если надо. |

Метрики в UI: **per-path** RTT/jitter/loss + агрегат после дедупа (то, что видит «как до сервиса»).
